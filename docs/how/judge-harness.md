## Steps

- The harness is Python 3, standard library only (no `pip`, no third-party package: a package is a dependency, `docs/how/add-or-change-a-module.md` does not cover it, ask Ghost). It is not a Java module; `docs/modules.json` does not list it and `ModulesTest` leaves it out of the source.
- Tests run by hand from `agent-runner/`: `python3 -I -B -m unittest discover` (`-I` isolates it from `PYTHON*` variables and the current directory; `-B` writes no bytecode). Without `python3` the gate reports PENDING and stays green; the pinned image has it (E-081).
- The one door to the network and to a key is agent_runner/transport.py (2.2l), the counterpart of MOD-05. Until it exists no file imports `socket`, `http`, `urllib`, `ssl`, `anthropic` (or another network or model-client module in `guard.py`) or reads an environment variable that names a key; `agent-runner/tests/test_guard.py` fails on one.
- The kernel imports no model client (E-003); the harness reaches it only as facts with evidence (E-017). The judge is given no tool and reads a prebuilt summary (E-013). Nothing an applicant submitted enters the repository (E-014).
- The summary builder is `agent-runner/agent_runner/summary.py` (2.2c): the brief JSON and a checkout in, one text out, repository text only inside `~~~data` fences. Its goldens are `test/goldens/summaries/`; after reading `git diff`, rewrite them with `EVALUATOR_WRITE_GOLDENS=1 python3 -I -B -m unittest discover` in `agent-runner/`. Summaries of real repositories go only under `build/` (the CLI refuses elsewhere, E-014).
- The judge's answer is held to `agent-runner/schema/judgment.schema.json` by `agent-runner/agent_runner/judgment.py` (2.2d): `parse(text)` returns the answer or raises `JudgmentError` naming each broken field. There is no `jsonschema` library, so the validator is its own strict checker of that one file, and `check_schema` keeps the file inside the subset a structured-output feature accepts (objects with every property required and `additionalProperties` false, string enums, integer and number ranges, arrays of objects or strings, a description on every node); the module's docstring lists it. The kind has six values (E-082) and its description in the schema is the judge's precedence rule, which the 2.2e prompt quotes: change the wording there, not in a copy.
- The judging prompt is `agent-runner/prompts/judge.instructions.md`, `judge.template.txt` and `judge.hash` (2.2e), with the answer schema above; `agent-runner/agent_runner/prompt.py` renders it (`render(summary)` is the exact text sent) and hashes it. The template's first line is `template-version: N`. The hash line is `sha256 <hex>`: the SHA-256 of the instructions' bytes, the schema's bytes and the template version, not of the summary and not of the template body (the golden holds the body; change it and bump the version). `agent-runner/tests/test_prompt.py` refuses a stale hash line; after changing the instructions, the schema or the version, run `python3 -B -m agent_runner.prompt write-hash` in `agent-runner/` (without `-I`, which would hide the package) and read the diff. The golden `test/goldens/prompts/judge-summary-notes.txt` is rewritten with `EVALUATOR_WRITE_GOLDENS=1` as the summary goldens are. The instructions quote the schema's `kind`, folder-class and tier descriptions through `{{kind_rule}}`, `{{folder_classes}}` and `{{tier_rule}}`: change that wording in the schema, never in the prompt. Their sources in `docs/judges/` are listed in the docstring of `agent-runner/agent_runner/prompt.py`; no real repository, owner or person is named in a prompt file (E-014), and the calibration labels are not prompt material.
- The judge is `agent-runner/agent_runner/judge.py` (2.2f): `Judge.judge(prompt, model, run)` returns an `Answer` (raw text, input and output tokens); `prompt` is a `RenderedPrompt` from `judge.rendered(summary)` (the text, the prompt hash of 2.2e and `summary_hash(summary)`, the SHA-256 of the summary's UTF-8 bytes). Tests above this slice use `FakeJudge` (scripted answers in order, `FakeJudge.unparsable()`) or `ReplayJudge`, never the network; a replay raises `MissingRecording` and holds no judge to fall to, and the run number is in the key. The recordings file is JSON lines, fixed in `judge.py`'s docstring: line 1 `{"version": 1}`, then one sorted-keys line per recording (`answer`, `model`, `prompt_hash`, `run`, `summary_hash`, `tokens` with `input` and `output`), in key order; `judge.dumps` writes it, `judge_from_recordings(path)` reads it. Its fixture is synthetic and hand-written; recordings of real runs go only under `build/` and are never committed (E-014). The live judge of 2.2l will implement `Judge` in `transport.py`.
- The cost cap is `agent-runner/agent_runner/budget.py` (2.2g): `Budget(per_call, per_evaluation, per_trial, prices)` in tokens, each cap None (no cap, the default) or a number; `BudgetedJudge(judge, budget, output_limit)` is a `Judge` that reserves the prompt estimate plus the output limit, raises `BudgetRefused` (`.cap` names call, evaluation or trial) with the inner judge never reached, then charges the real usage. `estimate_tokens` is ceil(UTF-8 bytes / 3), at least 1, a reserve only; the API's counts (2.2l) are what is charged. `begin_evaluation` and `begin_trial` reset the two counters independently: an evaluation is one repository, a trial a whole run over many (so a trial cap is above an evaluation's). `budget.records` is the cost of every judgment (the number that sets the unlock price floor); `write_records` writes it under a `build/` directory only. A usage above its reserve is charged, flagged `over_reserve` and kept in `overruns`; a failed call releases its reserve. Dollars are off until a prices file is passed (`load_prices`; format in the module's docstring, a date in it); the real file does not exist and no agent invents one. The caps and prices are Ghost's: the code holds none, and the numbers in `agent-runner/tests/test_budget.py` and `agent-runner/tests/fixtures/synthetic-prices.json` are synthetic.
- The three runs are `agent-runner/agent_runner/ensemble.py` (2.2h): `judge_repository(judge, prompt, haiku, opus)` takes any `Judge` (a `BudgetedJudge` included) and returns a `Result` whose rules, run numbers (Haiku slot k is run k, its retry 3 + k; Opus run 1, retry 2), field records and statuses (ok, partial, refused) are in the module's docstring: change a rule there and in `agent-runner/tests/test_ensemble.py`, not in a copy. The mean and the 15-point split are for the 0 to 100 scores; Quality's 1 to 5 is the median with Opus above one step (a call for Ghost); a category with no majority goes to Opus (E-083). The model ids `claude-haiku-5-5` and `claude-opus-5-5` are defaults to confirm, not known ids (Ghost's question 3). The caller wraps the judge in a `BudgetedJudge` and calls `begin_evaluation` per repository; a refusal mid-way returns a partial result.
- Agreement with the calibration set is `agent-runner/agent_runner/agreement.py` (2.2i, E-084): `load_labels()` reads `calibration/`, `compute`/`build_record` give per field (ambition, quality_exact, quality_within_one, kind) the labels matched over all 30, the constant-answer baseline computed from the labels, `needed` and `live`; `write_record(record, records_dir)` writes `agent-runner/records/<prompt hash>.json` (sorted keys, byte-stable; the date is passed in; shape in the module's docstring); `is_live(records_dir, prompt_hash, field)` answers from a record's counts, and no record for the hash is not live (SC-05). A partial, refused or missing result for an id is a miss on every field and counted apart. **Live** (Ghost, 2026-10-25) needs both: the raw agreement at least 80 %, and the figure at least baseline + MARGIN * (1 - baseline), MARGIN being one half by default (**the size of the margin is the agent's proposal, for Ghost to confirm or change**; it is `agreement.MARGIN` and a parameter). Worked on the real 30 labels: Quality within one, baseline 27 of 30 (90 %), needs 95 %, so 29 (28 is 93.3 %); kind, baseline 23 (76.7 %), needs 88.3 %, so 27; Ambition, baseline 14 (46.7 %), the margin needs 22 and the 80 % floor binds at 24; Quality exactly, baseline 17 (56.7 %), the margin needs 24 (78.3 %) and the floor 24. Tests write records only under a temporary directory and from synthetic answers; a record built from real runs is the question of 2.2m and is never written by a test (E-014).
- A new Python file needs a test in `agent-runner/tests/`; a new part's check is in `TODO.md`.
- The kernel reads a final judgment with `evaluator score --judged <file>` (2.2j, E-085): the file is the 2.2d answer wrapped with the prompt's hash and the models, not an ensemble `Result`; its exact shape and what it changes are in `docs/how/command-line.md`. Nothing in `agent-runner/` writes the wrapper yet. The card's rules for the judged kind (2.2k, E-086) read `agent-runner/records/<prompt hash>.json` in Java (`ingest/` `AgreementRecord`, liveness recomputed from the counts as `is_live` does, the flag never read; the folder is `--records`) and are in `docs/how/command-line.md`; a change to `is_live` or to the record's shape changes `AgreementRecord` and its fixtures `test/fixtures/judged/records/` with it.
