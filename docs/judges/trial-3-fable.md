# Judge trial 3: Fable's authoritative scores for six repositories

Ghost, 2026-10-22: "spin up a fable instance to give an authoritative scoring" for Katana, Suite Builder,
Employee Evaluator, Neon Rain, the Jensen migration (private) and one suite Suite Builder generated
(atos-net-10-6-2026). One Claude Fable 5.1 judge per repository, read only, up to about 80 tool calls,
commit messages allowed (not on this repository, whose messages carry our scores). Each first classified
every folder as own code, own tests, own tooling, docs, generated, vendored, reference or fixture data,
then scored the seven metrics on the author's own work only, and listed the mistakes a fast evaluator
would make on that repository (`fable-pitfalls.md`, beside this file). A seventh Fable read the six
reports (not the code) and put them on one scale. These are the reference the Haiku instruction sets
will be measured against (E-055).

## Against the kernel and the earlier judges

The kernel's tools' half against Fable (tool / Fable): the atos suite Size 80 / 2 and Provenance 64 / 5 (it
cannot tell a generated repository); Katana Size 92 / 68 and Complexity 53 / 92; Neon Rain Maintainability
65 / 35; the Jensen migration Complexity 0 / 55 (its JavaScript and Python functions are too few and short to

On the three repositories trials 1 and 2 read, the earlier judges' mean of three sits near Fable: Opus 1.1–2.9
points, Sonnet 2.8–3.8, Haiku 3.1–3.8. Those three are well documented and are their author's own code: the
easy cases. The discriminating cases are the ones no earlier trial held: a generated repository and a plan.

## Where the scale itself is doubtful (the seventh Fable's notes, for Ghost)

- Ambition mixes the scope posed with the scope attempted: a plan (Neon Rain) and a built system scored alike.
  Two fields, or ambition marked unverified when Size is under 10.
- Navigability rewards being small and rewards a repository built to the checklist (this one). Score it above
  a size floor, and name the mechanism (routing table, enforced imports).
- A generated repository breaks every metric: the card should say "generated by <tool>; the author's own work:
  3 lines" and print no scores, or score only the author's commits.
- A plan-only repository should read "nothing built yet" and withhold Size, Complexity and Maintainability.
- Provenance deducts "agent-written under one director" inconsistently: separate evolution over time from
  authorship, and state the rule once.

## What it says for the Haiku experiment

Each repository's pitfalls are what a quick reader gets wrong, and with what to look at instead: counting
generated, vendored, reference and fixture lines as the author's; crediting tests named but absent; reading
an AI co-authored history as either a dump or as solo work; judging a hard problem by its short files. A
Haiku instruction set that makes the reader classify folders first, from evidence (generator headers, build
excludes, `.gitattributes`, READMEs in the folder), is the first candidate.
